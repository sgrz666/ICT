# _tools/prompts/ — 五项测试的任务原文

## 职责

阶段 E 的**输入**。六个文件都是喂给官方 `dsh --profile headless` 的原始 prompt 文本，逐字对应任务书里的五项要求，加一个只读探针。

## 内容

| 文件 | 对应验收 | 原文要点 |
|---|---|---|
| `t1.txt` | 测试 1 工作区探索 | 自主看目录、读 README 与主要源文件、概括职责、**列出实际调用过哪些工具** |
| `t2.txt` | 测试 2 自主创建并运行 | 写一个支持加减乘除的 Python 计算器 + 测试，**自行执行**，按工具返回判断成败 |
| `t3.txt` | 测试 3 失败后自主修复 | 跑现有测试 → 分析失败 → 改程序 → 重测直到确认修复；修不好就如实汇报 |
| `t4.txt` | 测试 4 多工具组合 | 读工作区 → 定简短计划 → 新增带输入校验的命令行功能 → 跑测试 → 汇报改动文件与真实结果 |
| `t5.txt` | 测试 5 中断与恢复 | 「还有什么没做完？先回顾你已经做过的事」——配 `--session-id` 复用旧会话，用来检验上下文与工具历史是否真被恢复 |
| `probe_shell.txt` | 环境探针 | 只跑 `python -m unittest -v` 并汇报，**明令不许改文件**；用于隔离「阻塞来自沙箱」与「模型不会做事」 |

## 与上下层的关系

- 消费者：[../run_headless.sh](../run_headless.sh)（第二个参数就是这里的文件名）。
- 产出：`../../_logs/<stem>.jsonl`；索引见 [../../_logs/README.md](../../_logs/README.md)。
- 结论：[../../harness-validation-reports/agent-loop-test-report.md](../../harness-validation-reports/agent-loop-test-report.md)。

## 已知的坑与纪律

1. **不改原文措辞**。任务书怎么说就怎么写，否则「模型是被这句话驱动的吗」失去可比性；同一 prompt 在不同环境下的两次运行（如 `t2` 与 `t2_fixed`）才构成有意义的对比。
2. 用文件而不是命令行内联字符串传 prompt：中文与引号在 bash / pwsh 之间极易被吃掉，`run_headless.sh` 用 `cat` 读文件再传参。
3. 新增测试请同轮在本表加一行，写明它对应哪条验收。
4. prompt 里不要写绝对路径以外的敏感信息，也不要指示 Agent 越出工作区——除非像 `t5`/UI 审批那样，目的就是观察权限边界。
