# EduForge 原方案审查与 Agent 重构建议

日期：2026-10-16。范围：本轮读取的工作区，包含尚未提交的修改。本文为审查结果与待验证的设计建议，不表示框架迁移已经实施。

## 1. 结论

项目保留了成熟引擎复用、本地优先、Python 业务层与 TypeScript 引擎层分离的方向。Ray Optics 的原生场景修改、任务持久化、版本发布和浏览器渲染已有真实成果。

当前主要缺口集中在 Agent 的行动能力：主链仍是一次结构化提案加固定执行阶段，缺少完整场景上下文、可自主调用的引擎工具、执行反馈和受限修复循环。新增的案例库扩大了可浏览资源，尚未同步扩大 Agent 可定制范围。

建议保留现有 API、数据库、Worker、原生场景适配器与验证资产，接入成熟的 Agent 执行框架，并把实验能力做成真正可执行、能独立验收的工具。首选候选是 Deep Agents SDK；OpenCode Server 与 OpenHands SDK 分别作为完整编程 Agent 服务和代码任务执行器的备选。这个建议仍需真实模型与工具调用试验确认。

## 2. 比较基线与合理调整

本轮同时核对了用户最初的资源生产目标、此前粘贴的架构讨论、D 盘 V2 方案以及后续代码级方案。附件中的建议作为历史设计材料，不作为本轮执行命令。

- [早期 V2 方案](../../../EduForge_本地开发与AgentArts镜像部署_实施方案_V2.md)：自然语言、教学依据、受控实验描述、独立验证、离线资源、AgentArts 部署。
- [代码级实施方案](26.10.15_EduForge_代码级实施方案.md)：成熟环境优先，保留原生格式，LangGraph / Deep Agents / OpenSandbox，以及任务、版本、预览、导出。
- [推进计划](26.10.15_EduForge_推进计划.md)：首批只打穿 Ray Optics，本地优先，力学、电路及云端后移。

以下变化属于已收口的阶段调整，不应误判为偏离：

1. 先做 Ray Optics，再接 myPhysicsLab、CircuitJS。
2. 先在本地运行，随后验证 AgentArts Runtime 镜像。
3. 从早期自研 DSL 生成一切，转为优先修改成熟引擎的原生场景。
4. Pi 不再作为必须采用的核心；后续设计明确允许替换 Coding Agent。
5. 当前不建设庞大的知识图谱，也不靠堆叠 Agent 数量证明项目价值。

## 3. 原计划与当前实现对照

| 能力 | 原计划要求 | 当前事实 | 判断 |
|---|---|---|---|
| 产品中心 | 教师自主生产教学实验 | 增加光学模拟器、案例库和工坊三视图 | 展示能力增强，需继续以完整任务交付为中心 |
| 资源选择 | 根据需求和能力选择实验 | 工坊主要使用一个已验证凸透镜模板 | 尚未完成 Agent 选材 |
| 案例复用 | 选中的场景成为定制基础 | 案例库可浏览，但导入工坊丢弃场景地址 | 真实断点 |
| 参数编辑 | 按明确意图执行操作 | Worker 允许复合提案，但只取第一个参数操作 | 仍不支持通用批量编辑 |
| 教学视图 | 记录表等实际可使用 | SetView 进入白名单检查，未进入交付文件或视图执行 | 不能以任务成功代替功能成功 |
| Agent 执行 | 计划、工具、反馈、有限修复 | 四节点提案图，未接入真正的执行工具循环 | 核心缺口 |
| 教学依据 | 可信课程内容与科学依据 | 主规划路径主要读取参数和视图清单 | 尚未完成课程依据接入 |
| 科学验证 | 独立观测值对照参考 | 实像已有探测器对照；新增边界分支直接判通过 | 验证标准被削弱 |
| 迭代版本 | 在当前版本上持续修改和恢复 | 普通提交仍使用初始基础版本；种子回滚预览缺少产物 | 用户闭环未完成 |
| 离线交付 | 当前版本对应完整可运行资源 | 正式发布仍是原生 JSON；网页包独立存在 | 尚未接通交付链 |
| 预览隔离 | 工作台与预览分属不同来源 | 同源 iframe，允许脚本和同源能力 | 与原设计存在实质差异 |
| 评测 | 正确目标、实际运行、成本和失败样例 | 模式分流已实现，但真实模式只检查接受与拒绝 | 不能证明端到端效果 |
| AgentArts | 同一个核心 Agent 的真实 Runtime 运行 | 有入口兼容替身；缺真实 SDK 和部署验证 | 后续阶段，尚未验收 |

与上次审查相比，以下改进确实存在：

- 模型评测模式与规则模拟模式已出现独立执行分支，不再统一调用规则模拟器。
- Worker 已接受参数操作与视图操作组合，焦距边界不再触发此前的 NoneType 异常。

- 工作区已建立 Git 仓库。

这些改进需要保留；其中部分验收仍只证明状态或接口可用，尚未证明教师目标实际完成。

## 5. 需要优先处理的代码问题

优先级含义：P1 应在下一次对外演示或真实数据使用前处理；P2 应在单引擎 MVP 收口时处理。

### P1：数据库异常恢复会结束无关进程并删除数据库

证据：[tools/run_db.py](../code/eduforge/tools/run_db.py)，第 38–46 行附近。

第一次启动遇到任何异常后，会按进程名终止所有 postgres.exe、pg_ctl.exe，再删除整个指定数据目录并重建。这不是仅针对当前服务的恢复，也没有区分临时不可用与数据库损坏。

本轮通过拦截 subprocess.run 和 shutil.rmtree 验证了该路径，没有执行终止或删除。它与原方案的保留数据库、保留历史资源要求冲突。

处理方向：只管理本任务记录的进程；启动失败时保留原目录并返回可诊断错误。需要重建时使用新目录或可恢复备份，不能把清空数据作为通用异常恢复。

### P1：第二次普通修改使用旧基础版本，任务会停在运行中

证据：[App.tsx](../code/eduforge/apps/teacher-web/src/App.tsx) 第 288 行附近、[repositories.py](../code/eduforge/python/src/eduforge/infrastructure/db/repositories.py) 第 275 行附近、[worker/main.py](../code/eduforge/python/src/eduforge/worker/main.py)。

App 传给普通需求提交框的是创建时的 exp.base_revision，没有随当前 head 更新。首次发布后再次提交，API 接受任务；发布时触发 RevisionConflict，而 Worker 未把该异常转成可解释终态。

本轮临时数据库复现结果：第二次提交返回 HTTP 202；Worker 抛出 RevisionConflict；任务仍为 running，阶段为 packaging。

处理方向：明确当前编辑基线并随版本选择更新；冲突必须返回结构化终态，保留候选供比较。

### P1：视图操作被接受，但没有执行

证据：[worker/steps.py](../code/eduforge/python/src/eduforge/worker/steps.py) 的 _order、_apply、building、packaging；[validation/policies.py](../code/eduforge/python/src/eduforge/validation/policies.py) 的 view_registered 检查。

视图操作只检查 view_id 是否登记；编辑和打包路径没有应用 visible，也没有把教学视图配置持久化为包装资源。多个 SetParameter 也只执行第一个。

本轮用真实 API、数据库、Worker 和 Engine Host 比较：

- 单独把焦距改为 15cm：成功。
- 改焦距为 15cm 并显示测量表：成功，但下载字节与前一任务完全相同。
- 只显示测量表：成功，交付 JSON 没有测量表配置。

因此新复合测试通过只证明任务能发布，没有证明记录表存在且可用。原首条验收中的物距调节也尚未作为受控参数提供。

处理方向：将教学视图作为可执行的包装层配置，真实生成表格、采集行为和导出；逐项验证用户要求是否产生结果。

### P1：无穷远像与虚像分支缺少独立观测验证

证据：[validation/policies.py](../code/eduforge/python/src/eduforge/validation/policies.py) 第 91–105 行附近。

当前分支根据请求参数计算参考类型，再把 expected、observed 写成相同常量，并直接 passed=True。

本轮故意提供实际焦距为 15cm 的真实上游仿真结果，但分别声明修改目标为 30cm、40cm，两种报告仍通过。这说明“边界不报错”已经修复，“边界物理结果被独立验证”尚未完成。

处理方向：先核对候选场景中的实际参数，再从出射光线方向、反向延长交点等观测检查相应工况；无法观测的检查明确记为未验证，不能写成通过。

### P2：案例导入丢失所选资源

证据：[App.tsx](../code/eduforge/apps/teacher-web/src/App.tsx) 第 175–182 行附近。

handleImportToStudio 的 _sceneUrl 未被使用，匹配表达式会选中已有凸透镜模板。

本轮 Chromium 操作选择“两面镜子成像”并点击 AI 定制，实际创建接口返回 template_id=optics.convex_lens。案例数量不能直接解释为 Agent 可定制资源数量。

处理方向：导入资源必须写入实际场景、来源版本、原生对象与能力清单。未经科学验证的案例保留其验证状态，不能自动继承凸透镜科学档案。

### P2：正式交付仍只有 JSON

证据：[worker/steps.py](../code/eduforge/python/src/eduforge/worker/steps.py) 第 262 行附近、[offline-package.ts](../code/eduforge/services/engine-host/src/export/offline-package.ts)。

Worker 发布 media_type=application/json，未接入网页包装、离线包构建、完整包登记与下载。独立网页包需要本机静态服务，这是可接受的形态调整，但需要真实随包启动器和下载闭环。

处理方向：把原生场景、教学包装、静态资源、来源与许可证、验证报告、启动入口打成同一交付包。下载后的版本必须与已验证版本一致。

### P2：模型评测仍会把错误目标记为成功

证据：[benchmarks/runner.py](../code/eduforge/benchmarks/runner.py) 的 run_deepseek_direct_task、run_agent_graph_task。

规则基线检查 task.check，两个真实模式主要检查能否被接受。本轮注入一个把目标 15cm 返回为 8cm 的规划模型，agent_graph 仍返回 PASSED。

此外，配置中的重复次数没有进入实际循环；评测未执行引擎、浏览器或下载流程。报告输出还随工作目录变化，出现工作区 output 和工程内部 output 两套位置。

无密钥测试只移除了 DEEPSEEK_API_KEY，未同时清理新增支持的 deepseek 等别名，测试隔离也应同步更新。本轮全量复测在独立进程中清空模型密钥变量，避免意外调用真实模型。

处理方向：统一目标匹配、预期拒绝原因、实际产物和运行效果的判据，再补重复、耗时、模型用量、修复次数。不能用提案接受率替代实验交付成功率。

### P2：iframe 属性没有恢复原方案的来源隔离

证据：[PreviewFrame.tsx](../code/eduforge/apps/teacher-web/src/components/PreviewFrame.tsx) 第 83 行附近。

同源页面同时允许 allow-scripts 与 allow-same-origin。本轮从预览内部实际读到了工作台 parent.document，证实其仍能访问父页面。原生模拟器视图也未形成独立业务来源边界。

处理方向：预览与工作台使用不同来源；包装页与原生模拟器可在预览来源内部同源。消息检查精确 origin、source、结构和当前版本。

### P2：种子回滚后无法恢复预览

证据：[experiment_service.py](../code/eduforge/python/src/eduforge/application/experiment_service.py) 与 [App.tsx](../code/eduforge/apps/teacher-web/src/App.tsx) 的 loadRevision。

种子版本有 native_data，但没有产物登记；loadRevision 只通过已登记产物载入预览。本轮点击回滚，head 成功迁回，但页面出现 ARTIFACT_NOT_FOUND，预览 iframe 被清空。

处理方向：种子也生成完整版本交付，或为可信 native_data 提供明确的只读预览路径。回滚测试必须验证画面和后续编辑。

### P2：保存调参仍会重新解释确定值

证据：[App.tsx](../code/eduforge/apps/teacher-web/src/App.tsx) 的 handleSaveTunedRevision。

当前把控件值转成自然语言再提交规划。未配密钥时，启动脚本自动添加固定 15cm 提案；配模型时也多一次重新解释的机会。

处理方向：保存当前调参使用结构化操作提交、校验和发布；自然语言任务使用 Agent 规划。两条入口共享执行和验证能力。

### P2：部署配置与实际路径尚未匹配

证据：[agent/Dockerfile](../code/eduforge/infra/agent/Dockerfile)、[compose.local.yaml](../code/eduforge/infra/compose.local.yaml)、[agentarts.py](../code/eduforge/python/src/eduforge/entrypoints/agentarts.py)。

Dockerfile 引用的 python/pyproject.toml 不存在；Compose 的 PORT=4000 与 Engine Host 实际读取的端口变量不一致；缺少完整 Worker 与业务服务编排。AgentArts 当前使用未安装 SDK 时的兼容替身。本轮未运行镜像或云端验证。

这些文件应继续标为待联调，不能作为可直接部署的证明。云端后置仍符合用户确定的本地优先路线。

## 6. Agent 为什么没有发挥作用

本轮运行时快照还发现：本机默认端口的 API、Engine Host 健康接口和工作台首页均可访问，API 只列出一个有效模板；但进程检查未发现 eduforge.worker.run 命令行 Worker。页面与引擎在线不能证明任务有人执行。用户测试的具体实例地址仍需核对，因此此处作为默认本地实例的排查线索，不推断其他部署。

应先补执行链健康检查：Worker 存活与最近心跳、任务领取记录、模型调用结果和失败终态；启动成功提示也应覆盖 Worker 实际存活。之后再验证新框架的工具行动能力。

当前主调用链大致是：

```text
手动选凸透镜模板
  → LangGraph：装载清单 → 列出控件 → 模型生成 JSON → 授权
  → Worker：编辑 → 落 JSON → 检查 → 发布

案例库 → 原生模拟器，是另一条浏览支路
```

主要限制是：

1. Agent 没有读到完整当前场景及历史修改，只拿到模板、基础版本 ID、参数和视图范围。
2. 模型没有注册可调用的场景读取、对象检查、修改、运行、验证、打包工具。
3. 引擎执行结果没有反馈给 Agent，让它修复失败或判断剩余需求。
4. 实际 code 路径仍返回 CODE_ROUTE_NOT_EXECUTED，Deep Agents 文件没有接入 Worker。
5. 课程教案检索器没有进入主规划路径；框架文件存在不代表能力已经启用。

这是从一次提案接口升级为可执行 Agent 的任务。增加引擎数量需要以完整工具链为前提。

## 7. 开源框架选择建议

以下功能依据官方文档；适配成本和推荐顺序是结合本项目的判断，并非已完成的横向实测。

| 方案 | 官方提供的能力 | 项目判断 |
|---|---|---|
| Deep Agents SDK | 基于 LangGraph 运行，支持自定义工具、MCP、上下文、文件后端和委派 | 首选试验对象，延续当前 Python 技术栈 |
| OpenCode Server | 无界面 HTTP 服务、SDK、会话与本地/远程 MCP | 希望直接接入完整编程 Agent 时的备选，需要独立服务适配 |
| OpenHands SDK | Python Agent、动作与观测工具、代码任务及 Agent Server | 适合作为复杂教学组件代码定制的执行器候选 |

Deep Agents 支持接入具备 tool calling 能力的 LangChain ChatModel。当前 DeepSeek 接入应先单独验证一次完整工具调用往返，再验证多步实验任务；不能用普通 JSON 对话通过代替工具调用通过。

本项目已规划 Deep Agents，但本轮环境检查显示相关运行依赖尚未安装、代码定制路径未执行。因此目前还没有实际用上这一执行框架的能力。

## 8. 建议的目标架构

```text
教师需求 + 当前实验版本
        ↓
业务 API / 会话与任务持久化
        ↓
Deep Agents 主 Agent（第一候选）
  读取上下文 → 调工具 → 观察结果 → 继续 / 有限修复
        ↓
实验工具服务（类型明确，可独立验收；后续提供 MCP）
  ├─ 资源检索和真实导入
  ├─ 原生对象、参数和能力检查
  ├─ 原生场景修改
  ├─ 教学包装与数据记录
  ├─ 实际仿真与浏览器检查
  └─ 离线打包与受控发布
        ↓
现有 Engine Host / Worker / PostgreSQL / 产物存储
        ↓
本地成功后，再适配 AgentArts Runtime 入口
```

Agent 决定操作及修复；实验引擎执行科学模型；验证器决定能否发布。验证报告、版本号、哈希必须由执行服务产生，不能由模型自报。

优先保留现有领域协议、数据库、任务租约、版本记录、上游引擎和可靠的实像验证。主 Agent 替换的是一次性 JSON 提案层，不需要重写整套前后端。

| 工具建议名 | 必须实际完成的动作 | 返回的事实 |
|---|---|---|
| search_experiments | 检索可信资源及能力 | asset_id、引擎、可用操作、验证状态 |
| open_experiment | 导入所选原生场景，建立版本 | 实验 ID、基础版本、来源 |
| inspect_scene | 读取当前版本对象、参数、单位及限制 | 实际对象与当前值 |
| apply_scene_patch | 在候选副本上执行完整操作列表 | 新候选 ID、参数差异、错误 |
| configure_teaching_views | 生成真实记录表、图表和控件包装 | 包装配置、行为与数据字段 |
| run_validation | 调引擎、独立参考和浏览器检查 | 实际值、期望值、通过项与失败项 |
| build_package | 组装已验证候选的离线资源 | 包路径、资源清单、哈希 |
| publish_revision | 检查执行权、验证结论和版本基线后发布 | 发布版本及下载入口 |

耗时操作返回 job_id，通过状态查询获得结果，避免主 Agent 阻塞等待浏览器。每个工具携带实验版本和任务上下文，身份由服务端注入。

同一组工具可以先用 Python 函数调用现有 HTTP 服务，随后增加薄 MCP 包装层。不要为框架替换重新实现底层实验操作。

代码定制另设受限执行器，仅在已有参数和教学组件无法完成需求时使用；任务工作区、导出范围、网络与执行时长独立限制。

## 10. 引擎扩展方式

先为 Ray Optics 做通“读、改、运行、验证、导出”。资源库可先检索全部已有案例，但只能执行已经声明并验证的操作；未适配的案例明确返回能力不足。

下一个引擎用来检验统一工具接口，而不是增加展示数量：可在 myPhysicsLab 和 CircuitJS 中根据下一张验收任务选择一个。各引擎共享工具语义，但原生修改、观测和科学验证分别实现。

不能把完整案例库一次性标为科学验证通过；也不应把多个引擎的全部底层工具同时塞进模型上下文。先根据资源和任务加载相关能力。

## 11. 建议的实施与验收顺序

### 阶段 A：修复事实与状态

- 移除异常即删库的恢复分支。
- 修复连续修改基线、版本冲突终态和种子版本预览。
- 修复案例导入、视图实际执行、保存结构化调参、完整离线发布。
- 统一评测目标匹配，补齐篡改对照与失败样例。

### 阶段 B：工具先独立可用

先直接调用工具完成任务，不经过模型。逐项核对场景差异、控件动作、数据记录和下载包；失败结果必须明确、可重现。

### 阶段 C：接入成熟执行框架

用 Deep Agents 和真实支持工具调用的模型执行同一批工具任务，记录每次工具名、结构化输入、实际输出、耗时和错误。不要保留“无密钥时自动固定修改成功”的产品表现；演示模式在界面明确标注。

如 Deep Agents 的同任务验证不满足要求，再让 OpenCode Server 或 OpenHands SDK 调用同一工具层对照，使用同一模型、任务、预算和正确性判据。

### 阶段 D：增加第二引擎并验证迁移

保留工具合同，替换具体引擎适配器。单引擎及跨引擎任务均达到验收后，再验证 AgentArts SDK、镜像架构、工具服务访问、持久化和云端调用。

### 具体任务验收

1. 选择“两面镜子成像”，导入后的原生对象仍是对应镜面场景。
2. 修改凸透镜焦距并显示记录表：焦距、表格、记录动作都实际改变，下载包保留它们。
3. 在刚才版本上继续修改：不退回初始版本，出现冲突时有明确终态。
4. 调参后保存：下载文件中的实际值与用户保存的确定值一致。
5. 无穷远像、虚像与实像分别用适用的实际观测验证；故意提供错误仿真时必须失败。
6. 断开外网后，通过随包本地服务仍能操作和记录。
7. 给模型返回错误参数，即使提案结构合法也不能被评测记为成功。
8. 不支持的能力明确解释或进入受限代码定制，不能偷偷替换为其他实验。
