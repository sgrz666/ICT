**修复前根因（精确到函数/调用链）**：

1. **双重执行**。`agent/deepagents_planner.py::DeepAgentPlanner.plan()` 用 `operations_from_trace(out["trace"])` 把模型成功的工具调用折算成 `EditProposal` → `worker/steps.py::Chain.planning()` 交给 `policy.authorize()` 写 `jobs.work_order` → `Chain._apply()` 再从**基线版本**逐条 `engine.apply()` 重放一遍 → `Chain.building()/validating()/packaging()` 全部以这份**重放产物**为准。模型验证的场景与发布的场景是两个对象，Trace 事实上成了业务状态源。
2. **未发布工作态只在内存**。`ExperimentToolService._sessions: dict[str, dict]` 是唯一存储；进程退出即失联，`_get_session()` 缓存未命中直接抛 `NotFoundError`，接管者无从恢复。
3. **交付字节有两套写法**。`Chain.building` 用 `scene_bytes()`（紧凑 + `\n`），工具路径 `build_package` 用 `json.dumps(..., indent=2) + "\n"` → 同一份场景两个 sha256，「验证过的哈希 = 发布出去的哈希」无从核对。
4. **候选/产物 id 只按 job 派生**。`derived_id(job_id, "revision")` 与工具层 `derived_id(job_id, f"candidate:{digest}")` 两套规则并存；前者对同一 job 的第二次编辑会撞主键，使「先改 A 再改 B」退化成「发布 A」。
5. **纯视图任务被误判**。`Chain._apply()` 在无参数修改时构造一个不含 `base_untouched` 的伪结果，随后 `bool(result.get("base_untouched"))` 恒为 `False`；上一轮把 `... or True` 的恒真修成了恒假，方向对但同样不成立。
6. **schema 无迁移机制**。整个 schema 是 `JOBS_DDL` 一串 `create table if not exists`，且在 `api/main.py`、`worker/run.py`、测试夹具三处重复执行；给已有表加列静默无效。

**实现方案与为何没有重建一套并行系统**：

- 新增**一张表 + 一个业务层 + 一个端口**，而不是新写一条执行链：
  - `experiment_candidates`（`job_id` 主键，一 job 一行；`native_data`/`teaching_views`/`edits`/`content_hash`/`state_version`/`status`/`validation_id`/`validation_hash`/`agent_trace`）；
  - `application/candidate_service.py` 是内容哈希与交付字节的**唯一实现处**：canonical JSON（键排序、浮点 12 位有效数字、整数值浮点归一为 int，`NaN/Infinity` 直接拒），`native_bytes`/`views_bytes` 取代两套写法，`Worker` 侧 `scene_bytes()` 改为委托它；
  - `agent/deepagents_runner.py::DeepAgentRunner` 作为执行端口，产出 `AgentRunRecord(candidate_id, content_hash, state_version, validation_id, agent_trace_ref, terminal_state)`；判定全部来自候选行与 `validation_reports`，不看模型自述。
- **Worker 复用工具层**：`Chain.building` 调 `ExperimentToolService.build_package`、`Chain.validating` 调 `run_validation`、`editing/packaging` 读同一行候选；`Chain._apply()` 已删除。旧的 `PlannerPort`（固定提案、单轮图）由 `agent/proposal_runner.py` **适配**到同一条候选写入路径，因此没有新增第二套语义，`benchmark` 的 `agent_graph`/`screening` 对照仍保留、定义不改。
- 保留而非删除仍被依赖的接口：`PlannerPort`、`StaticPlanner`、`DeepAgentPlanner`、`operations_from_trace` 都在，但生产配置（`worker/run.py --planner deep`）走 Runner；结构守卫 `test_single_publish_path.py` 继续钉「发布事务只有一条」。
- 版本 id 改为**内容派生**（`revision_id_for(job, content_hash)`、`artifact_id_for(job, name, digest)`），规则集中在持久层；发布后 `rebase` 候选基线，支持同一 job 连续编辑；测试改为读 `jobs.candidate_revision_id`，不再自己拼 id（拼 id 就是用第二套语义断言）。

**数据库迁移/向后兼容性**：
`schema_migrations(version, name, applied_at)` + `apply_migrations(conn)`：0001 复用 `repositories.JOBS_DDL`（DDL 唯一来源不变，守卫用例仍绿），0002 建新表。每条迁移一条事务、按版本号跳过已应用项，**旧库能升级、新库也不重复执行**。`job_id` 外键带 `on delete cascade`（既有用例清库路径依赖它）。没有 `down` 迁移——回滚仍靠备份重建，已上线的迁移 SQL 改了不生效（要加新版本号）。真实旧库升级由 `test_migration_runs_on_old_database_and_is_idempotent` 覆盖（先只建旧 schema，再迁移到 2）。

## 3. 本轮顺带发现并修掉的仓库缺陷

1. `Worker` 阶段失败时 `ConflictError`（工具层的拒绝）不被 `worker/main.py` 捕获，会让任务卡在 `running` 等租约过期，而不是可见地失败。现由 `Chain._terminal()` 统一翻译成 `TerminalError`（`VALIDATION_NOT_PASSED` / `CANDIDATE_CONFLICT` / `TOOL_CONFLICT` 等）。
2. 「不带 `experiment_id` 的再次 `open_experiment`」以前每次凭空新建一份实验；接上候选后与 job 已绑定的实验冲突。现改为**续用本 job 的候选**（这也是 `test_observation_drives_the_value_written` 暴露出来的真实语义问题）。
3. `application/candidate_service.py` 不能 import `experiment_tools.contracts.JobContext`：`experiment_tools/__init__.py` 会导入 `langchain_tools` → `service` → 反向回到应用层，形成环。改为本地 `JobScope` Protocol。
4. **`scripts/eduforge.ps1` 在 Windows PowerShell 5.1 下无法解析**：文件是 UTF-8 无 BOM，脚本里有中文提示，5.1 按 GBK 解码后字符串终止符判定错乱（`TerminatorExpectedAtEndOfString`，line 350–352），`doctor`/`test`/`smoke` 全部起不来。加 UTF-8 BOM 修复（内容一字未改），`doctor` 现已实测通过。此前各轮 README 写的「脚本可跑」在 5.1 下不成立，这条留痕在此。
